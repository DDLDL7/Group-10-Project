# CS 112 Final Project — Technical Specification

Grid Network Analysis, GridCare-Lite, ClinicCare-Lite

## 1. Tech stack (final)

| Component | Language | Framework/Libraries | Storage |
|---|---|---|---|
| Grid Network Analysis | Python | pandas, numpy, networkx, matplotlib, seaborn, plotly, folium, geopandas, geopy, scipy.stats, Streamlit or Dash, Jupyter | CSV files |

## 2. Grid Network Analysis

### 2.1 Data

Three CSVs generated by a seeded script (`random.seed(42)`), so every run produces identical data.

**utilities.csv**: Utility ID, Name, Alias, Code, Type (Generation/Transmission/Distribution), Country, Active (Y/N)

**substations.csv**: Substation ID, Name, Short Name, Region, Country, Latitude, Longitude, Voltage (kV), Capacity (MVA), Commissioning Year, Type (Distribution/Bulk Supply Point/Transmission), Status (Active/Inactive)

**lines.csv**: Line ID, Utility ID, Source Substation ID, Source Substation, Destination Substation ID, Destination Substation, Voltage (kV), Length (km), Capacity (MVA), Status (Active/Under Maintenance), Line Type (Overhead/Underground)

### 2.2 Required processing steps

1. Load and inspect all three CSVs
2. Clean: handle missing values, coerce numeric columns (`Latitude`, `Longitude`, `Capacity (MVA)`, `Length (km)`), drop duplicates, validate coordinate ranges
3. Validate relational integrity: every Source/Destination Substation ID in `lines.csv` must exist in `substations.csv`
4. Merge all three tables into one integrated dataset
5. Exploratory data analysis: substation counts by region, voltage distribution, top substations by line count, active/inactive counts
6. Build an undirected graph with NetworkX: substations as nodes (with region, voltage, capacity as attributes), lines as edges
7. Calculate: degree centrality, betweenness centrality, closeness centrality, PageRank, clustering coefficient, connected components
8. Run N-1 contingency analysis: remove the highest-centrality node, measure change in connected components
9. Geographic analysis: Folium map with substations colored by voltage, lines drawn as polylines
10. Business intelligence: utility footprint by region, capacity utilization flags, underserved region detection, asset age profile

### 2.3 Required outputs

- Cleaned and merged CSV
- Static charts (PNG) and interactive charts (HTML via Plotly)
- Interactive Folium map (standalone HTML)
- Interactive dashboard (Streamlit or Dash) with tabs: Overview, Network, Geography, Reliability, Search
- 2–3 page written report covering dataset description, cleaning steps, EDA findings, network analysis results including the N-1 test, and limitations of using synthetic data

## 3. GridCare-Lite

### 3.1 Roles

Administrator, Engineer, Technician, Customer Service Representative. Each role sees only its relevant screens. Enforcement happens in application logic and database permissions, not just by hiding UI elements.

### 3.2 Database schema (SQLite)

```sql
CREATE TABLE users (
    user_id INTEGER PRIMARY KEY AUTOINCREMENT,
    username TEXT UNIQUE NOT NULL,
    password_hash TEXT NOT NULL,
    role TEXT NOT NULL CHECK (role IN ('admin', 'engineer', 'technician', 'customer_service'))
);

CREATE TABLE substations (
    substation_id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    region TEXT NOT NULL
);

CREATE TABLE outages (
    outage_id INTEGER PRIMARY KEY AUTOINCREMENT,
    substation_id INTEGER NOT NULL,
    reported_by INTEGER NOT NULL,
    description TEXT,
    severity TEXT,
    status TEXT DEFAULT 'Open' CHECK (status IN ('Open', 'In Progress', 'Resolved')),
    reported_at TEXT DEFAULT CURRENT_TIMESTAMP,
    resolved_at TEXT,
    FOREIGN KEY (substation_id) REFERENCES substations(substation_id),
    FOREIGN KEY (reported_by) REFERENCES users(user_id)
);

CREATE TABLE work_orders (
    work_order_id INTEGER PRIMARY KEY AUTOINCREMENT,
    outage_id INTEGER NOT NULL,
    assigned_technician INTEGER,
    scheduled_date TEXT,
    status TEXT DEFAULT 'Pending' CHECK (status IN ('Pending', 'Scheduled', 'Completed')),
    FOREIGN KEY (outage_id) REFERENCES outages(outage_id),
    FOREIGN KEY (assigned_technician) REFERENCES users(user_id)
);

CREATE TABLE complaints (
    complaint_id INTEGER PRIMARY KEY AUTOINCREMENT,
    outage_id INTEGER,
    logged_by INTEGER NOT NULL,
    description TEXT,
    logged_at TEXT DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (outage_id) REFERENCES outages(outage_id),
    FOREIGN KEY (logged_by) REFERENCES users(user_id)
);
```

`substations` table is populated by importing the cleaned `substations.csv` from the Grid Network Analysis component, so outages can only be logged against real substation IDs.

### 3.3 Screens (PySide6)

1. Login screen — routes to the correct dashboard by role
2. Outage dashboard — table view of open outages, filterable by region/status
3. New outage form — substation picker, description, severity
4. Work order assignment screen (admin only) — assign technician, set scheduled date
5. Technician view — that technician's own assigned work orders, with a mark-complete action
6. Customer complaint log — form, optionally linked to an outage ID
7. Reports screen — open outage count, average resolution time, outages by region

### 3.4 Required workflow (must work end to end)

Engineer logs in → records outage against a substation → admin reviews → admin creates work order → technician assigned → technician views assigned task → technician sets status to In Progress → technician records work completed → outage marked Resolved → dashboard updates → customer service views/links related complaints.

### 3.5 Required error handling

Invalid dates, empty required fields, unauthorized function access, duplicate entries, incorrect credentials, references to non-existent substations. All of these must fail gracefully with a clear message, never crash the app.

## 4. ClinicCare-Lite

### 4.1 Scope boundary (hard requirement)

Administrative and communication only. Must never diagnose, interpret symptoms, calculate risk, recommend treatment, or prescribe. Any automated check is limited to structural validation (are required fields present, are values the right type), never interpretation of medical meaning.

### 4.2 Roles

Clinician, Patient.

### 4.3 ID and password rules

- Clinician ID: 8 digits, ending in `0000`
- Patient ID: 8 digits, ending in a registration year between 2022 and 2028
- Password: minimum 8 characters, at least one uppercase, one lowercase, one digit, one special character (`!@#$%^&*`)
- Passwords hashed with bcrypt before storage

### 4.4 Data model (JSON files)

**users.json**: user ID, hashed password, name, email, role, theme preference

**health_tasks.json**: task ID, title, description, due date, clinic ID

**task_submissions.json**: patient ID, task ID, file path, timestamp, review status, notes

**messages.json**: sender ID, recipient ID, timestamp, content, read status

**clinics.json**: clinic ID, name, assigned clinician ID, registered patient IDs

All JSON writes must use `f.seek(0)` followed by `f.truncate()` before `json.dump()`, otherwise old trailing content corrupts the file.

### 4.5 File handling rules

- Accepted formats: `.txt`, `.csv`, `.pdf` only
- Renamed to `patientID_taskID.extension`
- Stored under `submissions/clinicID/patientID/`
- Timestamped on upload
- Verified for file type, file name, file size, task ownership, and submission status before accepting

### 4.6 Review workflow

Categorical outcomes only, never a numeric score: `Pending`, `Reviewed — Normal`, `Needs Follow-up`, `Escalated`. Each review records reviewer, date, outcome, notes, notification status.

### 4.7 Messaging

Patient-to-clinician and clinician-to-patient messages, plus clinic-wide announcements. Persistent on-screen notice that the channel is not monitored continuously and must not be used for emergencies. Messages store sender, recipient, content, timestamp, read status. Patients must never see another patient's conversations.

### 4.8 Wellness engagement tracker

Private Engagement Points for on-time task completion and appointment attendance. Visible only to the patient who earned them. Must never be turned into a leaderboard or used to compare patients against each other.

### 4.9 Analytics

Clinician view (aggregated, clinic-wide): appointment no-show rate, task completion rate, pending review count, average review turnaround time, monthly task volume, overdue submission count, announcement reach, submission trends.

Patient view: their own history only, never another patient's data.

### 4.10 Screens (Flask/Jinja2 templates)

Clinician dashboard: health-task creation, patient selection, due-date setting, submission filtering, file preview/download, categorical review, review notes, patient messaging, clinic announcements, operational analytics.

Patient dashboard: assigned tasks, instructions and due dates, file submission form, submission status, clinician feedback, review outcomes, appointment reminders, inbox, secure messaging, theme selection, private engagement history.

### 4.11 Required error handling / test cases

Invalid clinician/patient IDs, weak passwords, unauthorized record access, unsupported file types, oversized files, missing required fields, incorrect task ownership, duplicate submissions, messaging privacy violations, notification failure, patient-data exposure, any attempted diagnostic-scope violation.

## 5. Testing requirements (all components)

Every major test documents: objective, input, expected outcome, actual outcome, pass/fail, defect identified, corrective action, retest result. Use `unittest` or `pytest`.
